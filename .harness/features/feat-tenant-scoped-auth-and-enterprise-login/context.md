# 特性架构背景 — feat-tenant-scoped-auth-and-enterprise-login

## 一、 问题根因与痛点诊断

1. **全局 User 模型与企业私有账号冲突**：
   - 当前 Better Auth 基于全局唯一 `email` 驱动；
   - 在真实 ERP 场景下，企业员工（如车间工人、外聘经办）经常没有邮箱，需要通过手机号或自定义工号/用户名登录；
   - 若不同租户（如 A 租户与 B 租户）录入了重名的账号或手机号，系统在全局 User 下会将其误判为同一个人，造成严重的跨企业越权访问与数据泄露。
2. **开通租户时的密码覆盖漏洞 (Critical Bug)**：
   - 之前在 `tenant-management/service.ts` 中，若管理员开通租户时填写的邮箱已在全局存在，系统直接执行 `account.update` 覆盖其密码，导致老租户所有者被恶意改密。
3. **员工录入时的虚假密码输入框**：
   - 当在租户后台录入已存在的邮箱员工时，表单仍强制要求填写密码，但底层为了不覆盖老用户密码静默跳过了凭据更新，导致管理员以为修改了密码但实际未生效。

## 二、 目标架构设计 (Jev 置信度 91% 推荐模型)

### 1. 双平面解耦
- **总控中枢 (Control Plane)**：保留全局超管统一登录（针对平台内部运维人员）；
- **租户业务端 (Tenant Data Plane)**：采用“企业编码 (Slug) + 账号/手机号 + 密码”的三要素独立认证。

### 2. 租户私有凭据模型 (Tenant-Scoped Account)
在平台管控库建立带有租户作用域的复合凭证索引：
- 唯一约束：`@@unique([organizationId, account])`
- 租户 A 的 `admin` 与租户 B 的 `admin` 完全物理与逻辑隔离，各自独立维护加盐密码哈希。

### 3. Better Auth 无缝会话集成
- 验证通过后，调用底层适配器直接签发挂载了特定 `organizationId` 的官方标准 Session；
- 租户端完全复用现有的 Cookie 轮转、防 CSRF、双层 Context 缓存与 CASL 权限注入防线。
